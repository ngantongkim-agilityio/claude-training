# Frontend for Tax Invoice System

## Technology stack:

- Next.js 16
- React 19
- TypeScript
- Auth0
- TanStack Query
- Zustand
- React Hook Form
- Zod
- Tailwind CSS v4
- Shadcn/UI

Package manager:

```text id="a8gr8s"
pnpm
```

Never use npm, yarn, or bun.

---

## Source of Truth

Before implementing any feature:

1. Read the API contract documentation.
2. Follow existing request and response contracts.
3. Do not change API contracts from the frontend.

Backend APIs are the source of truth.

---

## Architecture

Application flow:

```text id="hprwqg"
Page
  ↓
Feature
  ↓
Components
  ↓
Hooks
  ↓
API Client
  ↓
Backend API
```

Rules:

- Keep pages lightweight.
- Business logic belongs in hooks or feature modules.
- UI components should remain reusable.
- Avoid placing API calls directly inside UI components.
- Prefer composition over inheritance.

---

## Next.js Rules

Use App Router.

Prefer:

- Server Components by default.
- Client Components only when required.

Use `"use client"` only when:

- React hooks are needed.
- Browser APIs are required.
- Interactive UI is necessary.

Do not convert entire pages into Client Components unnecessarily.

---

## State Management

Use the right tool for the right purpose.

### Server State

Use:

```text id="w3mduv"
TanStack Query
```

Examples:

- API responses
- User profile
- Invoice data
- Dashboard data

Do not duplicate server state in Zustand.

---

### Client State

Use:

```text id="u4r4ly"
Zustand
```

Examples:

- UI preferences
- Modal state
- Theme state
- Temporary client-side state

Keep stores small and focused.

---

## Data Fetching

Rules:

- Use TanStack Query for API requests.
- Centralize API calls in API client modules.
- Avoid fetch logic inside UI components.
- Reuse existing query hooks whenever possible.
- Use query keys consistently.

Prefer:

```text id="sm7qcv"
hooks/
api/
```

over inline requests.

---

## Forms & Validation

Use:

- React Hook Form
- Zod

Rules:

- Define validation schemas with Zod.
- Use zodResolver.
- Keep validation logic centralized.
- Do not duplicate validation logic across components.

---

## Authentication

Auth0 is the authentication provider.

Rules:

- Use Auth0 SDK.
- Do not implement custom authentication flows.
- Do not manually store tokens.
- Protect authenticated routes appropriately.
- Keep authentication logic centralized.

Authentication flow:

```text id="rfwrz0"
User
  ↓
Auth0
  ↓
Frontend
  ↓
Backend API
```

---

## UI Guidelines

Use existing UI components before creating new ones.

Preferred stack:

```text id="axemhs"
Shadcn/UI
Base UI
Tailwind CSS
```

Rules:

- Keep components small and reusable.
- Prefer composition.
- Avoid duplicate components.
- Follow existing design patterns.
- Keep styling consistent.

## Testing

Frameworks:

- Jest

## Documentation

Keep documentation synchronized with implementation.

When changing behavior:

- Update README if needed.
- Update usage examples if needed.
- Keep documentation accurate.

## Comments

- Add comments for business logic and non-obvious code.
- Comment authentication, authorization, security, and complex validation.
- Explain WHY the code exists, not only WHAT it does
- Keep comments concise and up to date.

---

## TypeScript Conventions

- Arrow functions are mandatory.
- Use `const` for helper functions.
- Prefer `async/await` over callbacks or Promise chains.
- Avoid function declarations unless required.
- Reuse existing types instead of redefining them.
- Avoid any unless there is a well-justified reason.

---

## Git Rules

Before commit:

1. Run pnpm lint
2. Run pnpm test
3. Review changed files
4. Propose commit message
5. Wait for user approval before commit

Never add:

- Co-Authored-By
- Generated by Claude
- AI attribution

---

## Anti-Patterns

Do NOT:

- Introduce new UI libraries without approval.
- Duplicate server state in Zustand.
- Place API calls directly in UI components.
- Convert pages to Client Components unnecessarily.
- Add dependencies without justification.
- Ignore TypeScript errors.
- Disable linting rules to bypass issues.

---

## Core Principle

Consistency > Optimization
Follow existing project patterns.
Prefer minimal, safe, incremental changes over large refactors.
